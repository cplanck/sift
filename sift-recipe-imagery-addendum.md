# Sift — Recipe imagery addendum

**Milestone:** M3a — Generated covers and cooking-step illustrations  
**Suggested repo destination:** `docs/recipe-imagery.md`  
**Status:** Implementation handoff, 2026-10-05. No benchmark has been run. Repo paths below are proposed; adapt to existing conventions after inspecting the Sift repo.

## 1. Product and design contract

Generated imagery enhances a valid recipe; it must never block importing, saving, reading, or cooking it.

| Surface | Visual treatment |
| --- | --- |
| Library and recipe detail | One selected cover; photorealistic food imagery when generated |
| Cooking step | Optional, quiet **muted monoline culinary illustration** |
| Missing cover | Neutral monochrome placeholder |
| Missing or unsuitable step illustration | Typography only; collapse the illustration space |

Preserve the established dark-first, Vercel-like, agent-first design:

- Centered content, no navigation sidebar. Near-black surfaces, restrained typography, generous spacing, subtle tonal separation. Reuse existing design tokens.
- Recipe cards and main sections have no outer border. Reserve faint neutral borders (approximately `rgba(255,255,255,.07)`) for controls, interactive chips, and discrete saved artifacts.
- No gradients, sparkles, glowing AI treatments, mascot embellishments, or decorative panels. Preserve the bowl + three dots mark and “agentic cooking” tagline.
- Keep the persistent “Ask Sift anything…” composer with voice/attachment controls. Expand conversation in place; render tool results inline. Preserve current recipe, servings, step, and cooking-session context.
- Cooking mode prioritizes the current instruction, relevant quantities, timers, and bottom timeline/next step. Show the latest assistant message compactly, with history expandable. Do not duplicate the full ingredient list below imagery or require stock photography for steps.

Default cover preference: **user cooking/uploaded photo → imported source photo → accepted generated cover → placeholder**. An explicit user selection overrides this preference. Removing a cover explicitly selects “none”; do not silently restore an older image.

## 2. Service, records, and job lifecycle

Add an isolated `RecipeImageService` used by UI actions and agent tools. Reuse Sift’s authentication, workspace isolation, R2 integration, and Inngest infrastructure.

Minimum records (extend existing equivalents rather than duplicating them):

```text
Recipe
  coverImageId?, coverSelection: auto | selected | none, coverRevision

RecipeImage
  id, workspaceId, recipeId, origin: user | imported | generated
  r2Key, width, height, mimeType, checksum, derivatives[], createdAt
  sourceUrl?, cookingPhotoId?, generationRequestId?
  model?, resolvedProvider?, prompt?, promptVersion?, settings?
  gatewayGenerationId?, generationCostUsd?, costSource?, durationMs?

CoverGenerationRequest
  id, workspaceId, recipeId, requestedBy, idempotencyKey
  recipeSnapshotHash, expectedCoverRevision, promptVersion, settings
  status: queued | running | ready | failed | cancelled
  candidateImageId?, errorCode?, createdAt, completedAt?

GenerationAttempt
  requestId, attemptNumber, gatewayGenerationId?, resolvedModel?, provider?
  status, costUsd?, costSource: actual | estimated | unknown, durationMs
```

Persist an immutable snapshot of the canonical recipe fields used in the prompt. Generated provenance stays attached after selection; expose “Generated by Sift” in review and the cover menu, without a badge on every library card. Costs use decimal USD; unknown is null, never zero.

Flow: **parse → review → persist draft → enqueue `recipe.cover.generate` → Gateway → validate bytes → R2 original + derivatives → candidate ready → explicit selection**.

- Generating during review persists a private draft first. “Save recipe” finalizes that same record, even while generation runs. Abandoned drafts follow the existing cleanup policy.
- Create the request and durable event/outbox atomically. Deduplicate by workspace + idempotency key; “Try another” intentionally creates a new request. Allow one active generation per recipe.
- Separate durable job stages for generation, upload, derivative processing, and completion. Retry storage/processing from retained output rather than buying another generation. SDK and job retries must share a bounded retry policy; do not multiply retries unknowingly.
- Retry transient provider failures with backoff. Validation, unsupported settings, and policy rejection fail without repeated generation. An ambiguous provider timeout can already be billed: reconcile available request metadata before reissuing; record every charged attempt.
- Completion only creates a candidate. `setCover` uses `expectedCoverRevision` to prevent stale clients from overwriting newer choices. Upload, remove, or cancellation invalidates pending selection intent; late results never replace a cover automatically.
- If recipe fields change after generation, mark the candidate as based on an earlier revision and offer regeneration. Recipe deletion/discard prevents attachment. Sweep unreferenced temporary assets under the repo’s retention policy.
- Authorize every request, status read, image selection, and R2 delivery against its workspace. Validate fetched/uploaded image size, MIME and decoded dimensions; reuse safe URL fetching for imports and strip unnecessary metadata from served derivatives.

Retain the original once. Use `sharp` in a compatible server runtime to create 4:3 derivatives at **320, 640, and up to 1200 pixels wide**, WebP with optional AVIF. Do not upscale or generate separately for each display size. Record actual derivative dimensions, use responsive `srcset`, and reserve the aspect ratio to prevent layout shifts.

## 3. Gateway adapter and prompt

Use the repo’s pinned AI SDK and existing server-side Gateway client/authentication. Image-only models use `generateImage`; some multimodal image models instead use `generateText` and return image files. Keep either path behind the same adapter. See [Gateway image integration](https://vercel.com/docs/ai-gateway/modalities/image-generation/ai-sdk).

```ts
// Service-facing contract; implement against the installed SDK version.
generateCover(input: {
  prompt: string;
  preset: CoverPreset;
  requestId: string;
}): Promise<{
  bytes: Uint8Array;
  mimeType: string;
  metadata: GenerationMetadata;
}>;
```

Generate **one candidate per request**. Each preset defines the exact model ID, SDK method, supported size OR aspect ratio, quality, provider options, timeout, and retry policy. Validate presets before spending. Models differ in supported dimensions; Grok’s documented integration uses `aspectRatio`, not `size`. Native 4:3 is preferred; otherwise document the supported source ratio and crop to 4:3. See [SDK size controls](https://ai-sdk.dev/docs/ai-sdk-core/image-generation) and [Gateway model-specific examples](https://vercel.com/docs/ai-gateway/modalities/image-generation/ai-sdk).

Centralize configuration:

```dotenv
AI_GATEWAY_API_KEY=                   # reuse existing server auth; never public
AI_IMAGE_MODEL=                       # exact benchmark-selected model ID
AI_IMAGE_PRESET=                      # validated size/quality/provider settings
RECIPE_COVERS_ENABLED=false           # staged rollout / kill switch
RECIPE_COVERS_AUTO_GENERATE=false      # keep false for v1
RECIPE_COVER_DAILY_BUDGET_USD=         # required finite workspace cap
RECIPE_COVER_MAX_REQUEST_USD=          # required finite per-request reservation
```

Reuse existing R2/Inngest secrets. Add workspace rate limits and reserve estimated maximum spend atomically before dispatch; reconcile against actual costs. If cost is uncertain, retain a conservative reservation. The kill switch disables new generation while existing images remain usable.

Build the prompt deterministically from bounded, structured recipe fields; do not add a prompt-writing LLM. Treat imported text as data, omit raw page instructions, and include only relevant ingredients/preparation. Persist rendered prompt and version, initially `recipe-cover-v1`.

> Photorealistic editorial food photograph of {title}, a finished dish made with {principal ingredients}, prepared using {method; cuisine only if known}. Realistic home cooking, natural portions and food texture. Dark neutral ceramic serving ware on matte dark stone or wood, soft directional natural light, restrained styling, three-quarter overhead view. Recognizable at thumbnail size, with space around the dish for a 4:3 crop. No people, hands, text, logos, packaging, unrelated props, or added ingredients. {Optional bounded user styling preference.}

Allow requests such as “less fancy” as styling preferences without changing the canonical recipe. Generated imagery is illustrative, not evidence of the actual cooked result.

## 4. Import and agent UX

Keep the existing Paste / URL / Photo entry points. Add a compact **Cover** block within review: beside recipe fields on desktop, inline on mobile, without introducing a navigation sidebar or separate image editor.

| State | Display and actions |
| --- | --- |
| Source image available | Selected source preview; Keep image, Generate cover, Upload photo |
| No image | Neutral placeholder; Generate cover, Upload photo, Continue without cover |
| Queued/running | “Creating a cover from this recipe…”; preserve current cover; Save recipe remains available |
| Candidate ready | Preview, “Generated by Sift”; Use cover, Try another, Upload instead |
| Failed/budget unavailable | Inline explanation; Retry when eligible, Upload photo, Continue without cover |
| Saved while pending | Recipe opens normally; completion exposes the candidate in its cover control and relevant inline agent result |

“Generate cover” buys a preview; **“Use cover” selects it**. Saving while pending keeps the current cover or placeholder until selection. “Try another” retains the selected cover and previous candidate until a replacement is ready; no automatic four-image grids or retry carousel. V1 generation is suggested, never automatic.

After import, the cover menu supports upload, generate another, select an existing cooking photo, and remove. Keep controls keyboard accessible; announce status changes politely without stealing focus. Errors must not obscure recipe fields.

Expose shared service operations as typed tools:

```text
generate_recipe_cover(recipeId, stylePreference?, idempotencyKey) → requestId/status
get_recipe_cover_status(requestId) → status/candidate/error
set_recipe_cover(recipeId, imageId, expectedCoverRevision) → updated cover
remove_recipe_cover(recipeId, expectedCoverRevision) → explicit none
```

Use the existing photo lookup/upload tools to resolve “Use my last cooking photo.” Generation returns immediately and later updates the same conversation result. Agent and UI mutations have identical validation, permissions, limits, and provenance. Ask for clarification only when the requested photo or recipe is ambiguous.

## 5. Benchmark model, resolution, and cost

Build `scripts/image-benchmark.ts`, versioned recipe fixtures, a blind review gallery, and `docs/image-model-evaluation.md`. Default to dry-run; paid runs require an explicit execution flag and finite spend cap. Save a resumable manifest; completed cases must not regenerate on restart.

Candidate shortlist: `bfl/flux-3-image`, `spacexai/grok-imagine-image`, and one explicitly pinned OpenAI image model available in the team’s Gateway catalog. Add Google only if results warrant a fourth candidate. The [FLUX catalog page](https://vercel.com/ai-gateway/models/flux-3-image) currently lists a $0.02 starting price and multiple resolution classes; this is a benchmark candidate, not a selected winner or a quote for every setting. Verify team access, exact controls and current prices at run time using the [Gateway catalog/pricing](https://vercel.com/docs/ai-gateway/pricing).

1. **Model screen:** 20 fixed recipes × 2 independent samples × 3 models = 120 outputs. Cover noodles, poultry, chili, pasta, salad, curry, steak, bread, cookies, soup, tacos, casserole, sides, bowls, and ambiguous/sauce-heavy dishes. Use the same recipe snapshot and prompt; choose each model’s nearest supported ~1024-class setting. Freeze quality and routing; log unavoidable differences and provider fallbacks.
2. **Resolution screen:** best one or two models × the same 20 recipes × 2 samples × supported ~768, ~1024, and ~1536–2048 classes. Record exact width/height, megapixels, quality, crop loss, and billed units; class names are not standardized. Mark unsupported settings N/A. Skip 4K initially. Reuse identical first-stage cases.
3. **Review actual UI outputs:** 320–400 CSS-pixel library cards at 1×/2×, mobile cards, and 1000–1200-pixel detail presentation. Judge all presets in the same layouts, including smaller sources at the intended detail size; no artificial upscaling to manufacture a 1200-pixel derivative.

Blind-rate recipe fidelity, ingredient fidelity, realism, appetizingness, house-style consistency, thumbnail clarity, and crop resilience from 1–5. Proposed acceptance rule: all dimensions ≥4, with no obvious wrong dish, invented prominent ingredient, distorted food, text/logo, or unusable crop. Record categorical rejection reasons; resolve reviewer disagreements before unblinding. This small sample is a screening result, not proof of a stable production rate.

```text
first-attempt acceptance = accepted designated first samples / recipes attempted
overall acceptance      = accepted samples / all planned sample attempts
cost per accepted cover = all generation spend, including retries / accepted samples
```

Count failed attempts in acceptance denominators; zero accepted samples means undefined/infinite cost, never $0. Report p50/p95 generation and end-to-end latency, technical failure rate, regeneration rate, and sample counts. For illustration, $0.02 / 50% = $0.040 per accepted cover, while $0.04 / 95% ≈ $0.042: the latter is more reliable but not cheaper on that metric.

Capture Gateway generation IDs, available response usage/cost metadata, and all attempts; reconcile delayed usage through [Gateway generation lookup](https://vercel.com/docs/ai-gateway/observability-and-spend/usage). When unavailable, use a dated pricing estimate and label it; never treat missing cost as free. Report storage/processing costs separately.

**Proposed launch gates:** ≥85% first-attempt acceptance, <$0.05 average generation cost per accepted cover, and acceptable detail/card presentation. Select the lowest-cost preset meeting these gates, using latency and consistency as tie-breakers; ~1024 is a hypothesis. If none qualifies, report the shortfall and revise the prompt/candidates before rollout. Include held-out recipe checks for the finalist, raw manifest, score sheet, representative failures, and exact winning config in the report.

## 6. Muted monoline culinary illustrations

Use a small, reusable, reviewed asset library keyed by cooking action. Do not generate imagery during cooking or make every step require an illustration.

- Near-uniform 2–3 px equivalent stroke at intended display size; rounded caps/joins; simplified geometric shapes with slight hand-drawn character.
- Single muted sage/gray-green stroke, initially `#536A63`, on transparent background over near-black. At most two restrained colors; no gradients, shadows, cartoon faces, detailed fills, or decorative clutter.
- Centered composition with generous negative space; illustration remains smaller and quieter than the instruction. Use the accent for decorative art, not essential text or controls.
- Initial actions: chop, slice, whisk, stir, sauté, simmer, boil, bake, drain, knead, rest, and plate. Prefer reviewed SVG assets for consistent strokes; AI-generated raster drafts may be curated into the library offline, retaining prompt/model provenance. Never execute unsanitized generated SVG.

Authoring prompt: “Muted monoline culinary illustration of {action and utensil}. Simplified editorial line drawing, consistent rounded stroke, muted sage #536A63, transparent background, centered with generous negative space. No text, shading, gradients, shadows, decorative props, or cartoon styling.” Verify actual transparency and stroke quality; a prompt alone does not guarantee either.

Store `illustrationKey: ActionKey | null` on canonical steps and maintain a versioned asset manifest. Use a deterministic mapping from structured action tags, or the existing extraction model constrained to the enum; choose null for ambiguous/composite actions. Editing a step re-evaluates its mapping. No additional per-step image-model call.

Render through one `StepIllustration` component, typically 96–160 CSS pixels. Hide decorative duplicates from assistive technology; convey all instructions and state in text. Avoid using generic art to imply precise doneness, temperature, or knife technique. Missing assets collapse cleanly. Validate the library for recognizable actions, consistent stroke, transparent edges, and unobtrusive desktop/mobile rendering before release.

## 7. Delivery and acceptance

Implement in order: records/service and durable job → Gateway adapter and benchmark → import controls and agent tools → illustration library/component → staged rollout.

- [ ] Text-only import saves successfully while Gateway is slow, down, or disabled.
- [ ] Duplicate submissions/event deliveries do not intentionally purchase duplicate generations; storage retries reuse retained output.
- [ ] Upload/remove/select during generation survives late completion; stale selection and cross-workspace access are rejected.
- [ ] Save-and-leave, reload, draft discard, recipe edit, failed upload, and regeneration preserve coherent state and provenance.
- [ ] One candidate is generated per request; acceptance is explicit; original and responsive derivatives persist in R2.
- [ ] Benchmark report includes costs, uncertainty, failures, display-size comparisons, and exact configurable winner; quality gates are met before enabling generation broadly.
- [ ] Desktop/mobile review and cooking screens preserve the design contract, accessible controls, current-step prominence, bottom timeline, and agent composer.
- [ ] Every unsupported illustration action renders typography only; cooking remains independent of image services.

Use focused service/job tests with mocked Gateway and R2, integration checks for authorization and concurrency, and end-to-end tests for import/save/late-completion flows. Keep live paid generation outside routine CI.

Track `generation_offered`, `requested`, `completed`, `failed`, `accepted`, `regenerated`, and `replaced_with_user_photo`, correlated by recipe/request ID without logging full recipes in analytics. Review acceptance and spend after opt-in rollout. Automatic generation remains a later, separately enabled policy after sustained >90% acceptance and acceptable cost; this addendum does not enable it.
